# 设计

## 前端边界

订单列表仍由页面编排 `useOrders`，日期选择器只产生 `YYYY-MM-DD` 字符串；网络请求继续经过现有订单模块和公共客户端。订单详情、支付、支付结果和退款页使用明确的业务目标路径返回，不调用浏览器历史回退作为唯一行为。

退款摘要和替代场次的 ISO 时间在展示层统一调用现有订单时间格式化工具。D 的影片标题、影院名称不在本 change 内自行补齐。

## 替代场次查询

原场次上下文增加 `cinemaId`，应用层构造查询条件时同时传入 `movieId`、`cinemaId`、排除的 `showId` 和半开时间范围。Mapper 在数据库侧增加影院条件，保持可售、余座聚合和稳定排序。查询结果仍是只读快照，进入选座页后重新读取权威座位图。

## 过期验证

订单过期由现有 `ExpiredOrderReleaseJob` 和 `OrderExpiryTransaction` 负责，状态迁移保持 `PENDING_PAYMENT -> EXPIRED`，并在同一事务中释放当前订单仍锁定的座位。验证只在用户明确授权的受控环境执行：临时通过运行环境覆盖开启调度，不修改 `.env` 或仓库配置；验证完成后关闭覆盖并查询订单与座位结果。全局调度包含其他领域任务，必须记录其影响并避免在共享库无窗口运行。

## 不变规则

- MySQL 是订单、支付、票和座位的权威来源。
- C 的认证和错误响应解析保持不变，C 的修复另行处理。
- D 的内容服务只通过公开契约接入，D 未确认前不实现消费者。
