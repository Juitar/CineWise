## Context

归档的 `agent-contracts-and-plan-validation` 已提供不可变 `ExecutionPlan`、`ExecutionPlanNode`、`PlanNodeStatus`、`FailurePolicy`、`ToolRegistry` 和 `ToolResult<T>`。节点进入运行计划后均从 `PENDING` 开始，但没有纯 Java 组件负责判断何时可开始、如何记录一次执行尝试，以及失败后如何跳过依赖分支。

本次由 B 负责，代码只位于 `agent.domain` 和 Agent 单元测试。Agent 详细设计已确定：无依赖只读节点可以并行、只读查询最多重试一次、失败节点只影响其下游、单次运行最多重规划两次；写工具必须等待后续确认能力，当前基础阶段一律禁止执行。A、C、D 的接口、数据和运行环境均不在本次范围内。

## Goals / Non-Goals

**Goals:**

- 为一个已校验计划提供无副作用的“查找可开始节点”能力，以及返回新运行快照的受控状态推进能力。
- 将节点尝试次数、已使用的只读重试次数和运行的重规划次数放入纯 Java 运行状态，不向既有 `ExecutionPlanNode` 增加持久化、Web 或框架字段。
- 防御性地再次检查 `ToolRegistry`：即使调用方构造了绕过计划校验的计划，写工具、未知工具和确认节点也不能被状态机选中或重试。
- 用单元测试覆盖并列只读节点、合法与非法状态推进、失败分支跳过、首次重试、二次失败和重规划上限。

**Non-Goals:**

- 不实现工具路由、并行线程池、工具调用、真实 `ToolResult` 产生、模型重规划、计划替换或最终回复。
- 不实现 `actionId`、参数摘要、确认等待、写工具、写工具结果恢复或 `WAITING_CONFIRMATION` 状态推进。
- 不增加数据库、Flyway、Redis、SSE、Controller、认证、Spring Bean、A/D 的真实工具或前端。

## Decisions

### 1. 运行状态与计划定义分离

新增不可变的运行状态对象，持有原 `ExecutionPlan`、按 `nodeId` 保存的节点运行信息，以及重规划次数。节点运行信息保存当前状态、尝试次数、已用重试次数、工具结果的最小结构化信息和跳过信息；每次状态机调用返回新快照，不修改入参。

不直接给 `ExecutionPlan` 或 `ExecutionPlanNode` 增加可变字段。计划是校验后的定义，运行状态是一次执行的过程记录；分开后，未来持久化层可以单独映射运行记录，也能避免调用方在 record 中直接改状态。

### 2. 可开始节点只按依赖和服务端白名单判断

状态机先筛选 `PENDING` 节点，再要求所有直接前置节点均为 `SUCCESS`。`CALL_TOOL` 节点还必须在 `ToolRegistry` 中登记为只读；`CONFIRM_ACTION` 和登记为写工具的节点永远不返回。方法只给出候选节点，实际并发数量和调用顺序由后续应用层执行器决定。

不把并行线程池或工具路由放入领域状态机。它们会引入 Spring 和跨模块依赖，且当前没有真实工具可验证；返回完整候选集合可以让后续执行器按配置控制并发。

### 3. 状态推进使用受限方法并保留结果事实

状态机只暴露“开始节点”“接受工具反馈”“标记非工具节点成功或失败”“请求重规划”等受限操作。开始仅允许 `PENDING → RUNNING`；成功和最终失败仅允许从 `RUNNING` 进入终态。`PROCESSING` 结果保持 `RUNNING`。所有终态拒绝再次开始或覆盖，避免后续执行器重复调用已完成节点。

工具反馈由调用方以已有 `ToolResult<T>` 传入，状态机只读取 `status` 和 `retryable` 等公共字段，不解释 `data` 的领域内容。这样不依赖 A/D 的 DTO，也不会把敏感原始结果放进运行状态。

### 4. 失败传播固定为图遍历

一个节点最终失败或检测到前置节点已跳过时，状态机从该节点反向依赖关系遍历所有传递下游的未开始节点，将它们设为 `SKIPPED`。这些节点统一记录 `autoSkipped=true`、`skipReason=UPSTREAM_FAILED` 和最初失败/跳过的来源节点 ID。独立分支不在遍历范围内，继续保持可执行。

不由调用方逐个标记下游节点，也不把跳过当作成功。集中图遍历可以避免多层依赖漏标、不同调用点给出不同跳过原因。

### 5. 重试额度和重规划额度分别计数

只读 `CALL_TOOL` 节点首次出现 `FAILED + retryable=true` 时，只有 `failurePolicy=RETRY_ONCE` 才从 `RUNNING` 回到 `PENDING`，同时记一笔已用重试；任意后续失败都为最终失败。`PROCESSING` 不消耗额度。运行级“批准重规划”单独检查次数小于 2 后再加一；本次不创建计划版本，也不把失败自动视为已重规划。

将两种额度分开，避免“工具重试一次”错误占用重规划次数，也避免单个失败直接消耗尚未真正发起的重规划配额。

## Risks / Trade-offs

- [纯 Java 状态只存在内存] → 本次只作为可单测规则；后续持久化 change 需把运行快照、版本和并发更新规则落到 MySQL/Redis。
- [状态机不实际调用工具] → 用 `ToolResult<T>` 的成功、失败、处理中反馈覆盖状态规则；真实路由接入后补应用层和集成测试。
- [手工构造的计划可能不符合校验器规则] → 状态机对工具白名单、写工具和确认节点再次拒绝，但不替代 `PlanSchemaValidator` 的完整结构校验。
- [失败后同时存在已开始节点] → 本次只自动跳过未开始的下游节点，不取消或覆盖已 `RUNNING`/`SUCCESS` 节点；后续并发执行器需要定义取消和结果竞争处理。
- [未来确认能力要使用 `WAITING_CONFIRMATION`] → 当前禁止该状态推进，后续确认 change 以新的 spec 扩展，不在这里预留绕过入口。
