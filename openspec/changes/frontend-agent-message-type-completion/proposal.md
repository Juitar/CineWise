# Agent 消息类型补齐检查

## 背景与目标

旧 PRD 和交互设计列出 11 个 Agent 消息名称，但最新 B 后端白名单、固定夹具和已合入前端只正式支持七类 payload。本文记录实际映射，避免 C 因旧名称重复增加确认类型，或在缺少 B 协议时猜测出行字段。

## 范围

- 以最新 `origin/dev` 的 B 类型、校验器、Controller/SSE、固定夹具、已合入 OpenSpec 和前端解析为准，核对 11 个旧名称。
- 明确 `ORDER_CONFIRM` 已由 `PLAN_CARD + actionId + actionType=CREATE_ORDER` 覆盖。
- 记录 `TRAVEL_ADVICE_CARD`、`ROUTE_CARD` 和退票确认仍缺少的 B 协议证据，并明确三项不阻塞当前主流程联调。
- 复验“历史消息 → runId → 运行快照”的确认结果恢复，补充浏览器层结果未知场景。
- 消费 PR #160 已合入的 `PLAN_CARD` 正式 DTO，按固定夹具严格校验并展示允许公开的推荐摘要。
- 定义 B 后续单独 change 补齐正式协议后，C 才能开始的前端接入和测试条件。

## 非范围

- 不扩展 `AgentCardPayloadType`，不新增运行时校验、安全投影、组件或样式。
- 不新增 `ORDER_CONFIRM`、`REFUND_CONFIRM` 兼容枚举，也不从旧 PRD 猜测字段。
- 不修改 B 的枚举、SSE、确认动作、A 的退票工具、D 的出行 DTO 或固定夹具。
- 不把 PR #160 的推荐字段扩展解释为新的出行、路线或退票消息类型。
- 不在本 change 接入 D 的 `getTravelAdvice` Tool；它先由 B 作为结构化只读 Tool 使用，后续卡片协议另开 change。
- 不复用 `agent-confirmation-pr145` worktree 的未提交代码或静态 `PlanRecommendation`。

## Owner 与依赖

- C：维护前端安全解析、投影、组件和恢复测试；只有固定协议齐全后才实现。
- B：提供正式消息/动作类型、字段校验、固定 JSON 夹具、事件生成与 SSE 映射。
- A：退票确认接入前，提供 B 确认后调用的正式退票应用接口和结果查询规则。
- D：向 B 提供出行建议和路线的公开安全摘要，但 C 不直接把 D 页面 DTO 当作 Agent 卡片协议。

## 验收结果

- 七类现有 payload 与 PR #156 的实现保持不变。
- 旧 11 个名称有明确映射，不把缺少两个确认枚举名误判为建单确认功能缺失。
- 缺少 B 正式类型或夹具的项目保持未实现，不出现兼容猜测代码。
- 三项待补协议不阻塞“多轮问答 → 推荐 → 建单确认 → 结果恢复”联调。
- 确认 POST 结果未知时，前端只按历史消息的 `runId` 查询原运行，不重发确认。
- 最新 `PLAN_CARD` 的影片、影院、价格、开场时间、推荐理由、来源和时效通过安全投影展示；缺字段、字段类型错误和未声明字段被拒绝且不推进游标。
- B 补齐协议后，C 可按本文规格创建后续实现任务并完成契约、投影、组件、工作区和恢复测试。
