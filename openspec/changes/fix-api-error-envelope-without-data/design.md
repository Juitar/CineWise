## Context

`apiRequest<T>()` 当前调用 `readApiResult()`，后者通过 `isApiResult()` 同时校验信封元数据和 `data`。后端错误信封的 `data: null` 会被 Jackson 省略，因此解析会在 HTTP 状态、错误码、401 会话处理和 403 CSRF 处理之前失败。

当前仓库没有正式的成功无数据 `apiRequest<T>()` 契约。成功调用都声明了具体返回类型，所以本次只放宽失败信封，不改变成功类型。

## Goals / Non-Goals

**Goals:**

- 让合法失败信封在缺少 `data` 或 `data: null` 时保留后端结构化错误。
- 保持成功响应的数据存在性检查。
- 明确区分 `401/201006`、`403/201009` 和 `403/201007`。
- 非 JSON、HTML、空响应和结构错误只返回安全通用错误，不包含原始正文。

**Non-Goals:**

- 不改后端响应格式或业务错误码。
- 不增加页面级兼容逻辑，不自动重放写请求。
- 不把 `ApiResult<T>.data` 全局改成可选，也不支持未被正式定义的成功无数据接口。

## Decisions

### 1. 分开校验信封元数据和成功数据

公共客户端内部使用只要求 `code/message/traceId` 的失败可识别信封，`data` 保持可选的 `unknown`。解析 JSON 后先校验这三个字段；HTTP 非 2xx 或 `code !== 0` 时立即按失败处理，不检查 `data`。

只有 `response.ok && code === 0` 时检查 `data` 是否存在且不为 null。当前所有正式调用都要求具体成功数据，因此缺少 `data` 或 `data: null` 时抛出 `INVALID_RESPONSE`；存在时直接返回经过存在性检查的数据，由泛型返回类型承接，不使用强制类型断言。

### 2. ApiError 使用已校验的安全消息

合法失败信封使用已校验的 `message` 作为 `ApiError.message`，同时保留 `status/code/traceId`。空白消息或结构错误不作为后端业务消息展示，改用固定安全文案。客户端不读取、拼接或记录完整响应正文。

HTTP 非 2xx 使用 `kind: 'HTTP'`；2xx 但业务码失败使用 `kind: 'BUSINESS'`。非 JSON、空响应、HTML 和非法 JSON 使用 `kind: 'INVALID_RESPONSE'` 及固定文案；不可解析 5xx 不泄露代理页、堆栈或 HTML。

### 3. 认证和 CSRF 按状态与错误码分别处理

- `401` 在合法信封解析后运行现有共享 `unauthorizedHandling` Promise，同一批并发响应只执行一次清理和跳转，再向每个调用方抛出原 `ApiError`。
- 写请求收到 `403/201009` 时清理内存旧 CSRF Token，尝试获取新 Token，但不重放原写请求；刷新失败也保留原 201009。
- 写请求收到 `403/201007` 时不清理、不刷新 CSRF Token，也不运行 401 处理。
- 其他已解析写响应继续按现有 CSRF Cookie/内存 Token 更新规则清理旧 Token。

### 4. 测试覆盖公共规则和现有调用方

公共客户端用表格用例覆盖 401、403、409、422、429、5xx、失败 `data` 缺失/null、非 JSON、空响应、HTML、非法结构、成功有数据和成功缺数据。单独验证并发 401、201009 刷新但不重放、201007 不清理也不刷新。

认证相关测试继续证明结构化错误不会被模块改写。退款回归通过现有 `createRefund()` 调用公共客户端，模拟 401、403/201009 和 409，断言收到真实 `ApiError`；不改退款页面或模块实现。

## Risks / Trade-offs

- [认证或 Agent 分支同时修改 `client.ts`] → 合并时以最新公共解析顺序为主，人工保留各自新增的 CSRF generation、取消和 SSE 独立逻辑，重新运行两边测试，不能整文件覆盖。
- [后端返回空白或结构异常的 message] → 不展示该内容，使用固定安全文案。
- [未来新增成功无数据或 data 可为 null 的接口] → 单独定义正式返回类型和明确的请求选项或专用方法后再支持，本 change 不提前全局放宽。

## Migration Plan

1. 先补公共客户端失败和成功边界测试，确认旧实现会失败。
2. 分离信封与成功数据校验，调整错误构造和 401/403 处理顺序。
3. 补认证、退款回归，运行完整前端检查和生产构建。
4. 若需要回退，只回退本 change 的公共客户端、测试和 OpenSpec 文件；后端和业务页面无需回退。
