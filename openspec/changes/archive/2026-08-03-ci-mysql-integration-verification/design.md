## Context

现有后端 `verify` 以 H2 提供快速反馈，真实 MySQL 测试通过五个环境变量分别开启。交易测试已经强制数据库名为 `cinewise_ticketing_concurrency_check`，但 CI 未提供该数据库；场次查询测试还依赖云端已存在的演示数据，不适合作为自动化质量门。

## Decisions

### 1. MySQL 集成验证使用独立工作流和一次性数据库

新增 `backend-mysql-integration.yml`，启动官方 `mysql:8.4` 服务，固定使用 `Asia/Shanghai` 时区，并创建 `cinewise_ticketing_concurrency_check` 和仅用于当前 Runner 的应用账号。工作流结束后容器和数据自动销毁，不连接共享云端数据库。

### 2. 只运行真实 MySQL 测试集合

现有快速后端工作流继续执行完整 `verify`。MySQL Job 显式运行场次、并发建单、订单生命周期、支付和退款五个集成测试，避免重复静态分析，同时让新增数据库测试是否进入清单保持可审查。

### 3. 由 Flyway 和固定种子建立可重复基线

五个测试共用隔离数据库。测试按自身 Spring 配置开启 Flyway 和固定种子；Flyway 重复启动只执行校验，种子初始化保持幂等。场次查询测试同步改为该模式，不再假设云端已有未来场次。

测试统一要求 MySQL 8.4。CI 数据库与应用统一使用上海业务时区；场次查询夹具额外使用应用注入的 `Clock` 选择未来场次，避免数据库系统时区漂移导致选中已开场记录。生命周期测试验证 V005 已成功执行，不把 V005 错当成永远的最新迁移版本。

订单过期的真实库用例把到期时间设置为业务时钟前一秒，避免 MySQL `DATETIME(3)` 截断 Java 纳秒造成伪边界失败；精确等号边界继续由固定时钟测试覆盖。

### 4. 数据库名称是误操作最终保护门

所有会修改数据的交易测试继续校验 `SELECT DATABASE()`。场次查询测试也增加相同检查。环境变量与测试常量都固定为 `cinewise_ticketing_concurrency_check`，配置漂移时测试在执行查询前失败。

### 5. CI 凭据只用于一次性容器

工作流使用明文但非敏感的临时密码，不读取 GitHub Secrets、`.env` 或生产连接信息。密码只在当前 Runner 的隔离 Docker 网络和日志掩码范围之外使用，不具备任何外部系统权限。

## Risks / Trade-offs

- 多个 Spring 上下文会重复校验 Flyway 和幂等种子，使 Job 比 H2 CI 慢；25 分钟超时为启动 MySQL 和并发测试留出余量。
- 测试类清单需要在新增真实 MySQL 测试时同步更新；PR 审查规范应把该同步作为数据库测试检查项。
- CI 验证迁移从空库到当前版本，不替代 A 对历史迁移、共享数据库兼容和受控发布的正式审查。

## Rollback Plan

若工作流不稳定，回退新增 workflow、场次测试隔离调整和本 change；现有快速后端 CI 与共享数据库均不受影响。
