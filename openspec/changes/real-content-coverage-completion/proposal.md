## Why

`real-content-provider-integration` 已把 NetStart 的影片、影院基础资料同步到缓存和快照，但用户可见的真实资料仍不完整：影片海报和简介被丢弃；影院页、首页仍直接写死旧的杭州演示内容；影院城市条件混用了 Provider 的 `ci` 与系统行政区划代码；同步只覆盖热映，且管理端无法查看或手动触发同步。当前还把影片、影院资料按 6 小时有效、7 天最大陈旧处理，导致已取得的真实资料会在短期故障后让位给 Demo，不符合“真实历史资料优先于固定演示资料”的目标。

本变更补齐“真实影片和影院基础资料从 Provider 到页面”的缺口。它不把真实内容误当成真实票务，场次、票价、库存、座位和交易仍由 A 的本地票务能力负责。

## What Changes

- 补齐影片海报、简介、上映状态/日期等 Provider 可提供的基础字段；海报地址必须在 D 的适配层规范化为 HTTPS，再进入 `MovieContent`、快照、缓存和 `MovieResponse.posterUrl`。
- 补齐影院的城市代码转换和可用坐标映射；系统内部始终使用行政区划城市代码，不把 Provider `ci` 直接当作页面 `location`。
- 补齐热映与待映的受控同步、字段质量和去重规则；未通过校验的数据不能覆盖已验证快照。
- 取消影片、影院基础资料按时间淘汰的规则：每个公开查询保留最新两次完整成功的真实资料版本，最新版本优先、上一版本兜底。真实资料无论距今多久都优先于 Demo，并明确显示最近同步时间和“正在展示最近成功同步资料”。
- 移除每日同步中由 10 req/min 保护值间接造成的“最多 8 部影片详情”上限。首次初始化先回填 Provider 实际支持范围内近一年的已上映影片和可取得的待映目录；此后每天只增量发现并更新新上映、待映状态变化和已有资料变更。回填与增量均按 Provider 支持的分页/游标或可恢复批次执行，页面仅在已同步的真实目录中分页、搜索和筛选。
- 开发环境默认启用已确认的 NetStart Provider，并由每天凌晨 3 点的定时任务同步真实影片、影院资料；不使用启动即同步作为常规更新方式。开发排障可显式关闭开关，生产或商业环境仍强制关闭该学习用途 Provider。
- 补齐按当前城市浏览影院：本期默认长沙并支持用户手动选择城市；浏览页不申请定位、不计算距离，定位仅保留给用户主动发起的基础路线。
- 在没有用户主动定位、手动切换城市或常用城市功能时，页面默认使用可配置的长沙行政区划代码 `430100`；它是全局演示默认值，不保存为用户偏好。
- 增加管理员可查询的内容来源状态和受控手动同步；不记录 Key、完整原始响应或受限文本。
- 增加仅供 A 后续使用的公开内容身份解析契约：按 `provider + resourceType + externalId` 批量唯一解析内部 `movieId/cinemaId`；明确输入校验、数值错误码、映射失效和歧义处理，不暴露 D 的 Entity、Mapper、Repository 或内容表。
- 由 C 将影院页和首页的影片/影院展示替换为已确认的内容 API；删除写死的杭州影院、演示距离、演示场次和演示起价。真实影片/影院没有 A 的可售场次时，页面只展示基础资料和无场次状态。
- 补齐 D、C、A 的测试、OpenAPI/类型、Mock 和真实开发环境验证材料。

## Non-Goals

- 不接入影评正文、用户评论、演员等未确认展示字段，不保存 Provider 原始响应。
- 不接入真实排期、真实影厅、实时库存、真实座位、真实订单、支付或退款；不以真实内容推断这些数据。A 将另建 `real-showtime-read-model` 和 `real-showtime-ticketing` 处理真实排期及后续交易能力。
- 不自动选择新的第三方数据源，不在生产或商业环境启用仅供学习用途的 NetStart。
- 不保存用户精确位置、位置授权结果或距离排序记录；它们不进入 MySQL、Redis、日志、快照、URL、画像或 Agent 轨迹，也不做持续定位。

## Owners and Required Decisions

- D：Provider 映射、内容模型、缓存/快照、同步、来源状态、质量校验和后端测试。
- A：为新增影片持久化字段分配并验证 Flyway 版本；确认真实内容与本地 Mock 场次的展示边界不变。
- A：已确认当前真实影片、影院任务不等待真实排期；后续真实排期数据源、`movie_show`、座位、价格和下单入口由 A 的独立 change 负责。
- C：确认 `posterUrl`、`summary`、上映状态/日期及来源时效字段的前端 DTO、手动城市和管理员同步交互；将首页、影院页接入 API，并删除虚构票务展示。
- B：无需改 Tool Schema；只需复核真实内容新增字段不进入 Agent 私有输入或输出。

## Acceptance Results

- 已同步且合格的真实影片，在 `GET /api/v1/movies` 和详情接口中可返回 HTTPS `posterUrl`；前端能显示海报或在空/加载失败时显示占位。
- 已同步且 Provider 可提供的影片简介、上映状态/日期和影院坐标可经标准化、缓存、快照和 REST 一致读取；Provider 缺字段时按字段规则为空或拒绝该条，不伪造值。
- 城市查询使用系统行政区划代码，不能因 Provider `ci` 差异导致真实影院查不到。
- 未选择城市时展示长沙，用户手动选择长沙后只查询和展示长沙影院；本期影院浏览不申请定位、不展示距离。
- 未定位且未手动选城时，首页和影院页默认查询长沙 `430100`；切换仅保留当前页面会话，不作为用户长期偏好保存。
- 首页、影片页和影院页不再把写死的虚构影片/影院当作真实数据展示；来源、同步时间、资料版本和降级提示保持正确。
- 管理员可查询最近同步状态，并能按确认后的限制发起一次同步；非管理员无权访问。
- 真实内容与 A 的 Mock 场次分开显示，未关联可售场次的真实内容不能显示价格、余座或“可购”。
- A 可通过 D 的公开身份解析契约安全取得内部影片、影院 ID；未匹配、重复或有歧义时不返回猜测结果。
- A 可一次解析同一来源、同一资源类型下最多 100 个外部 ID；未匹配、歧义或已失效的映射逐项返回稳定数值码，不影响同批其他有效结果。
- 在任意一次真实影片、影院同步成功后，后续查询优先使用保留的真实版本；Demo 只在首次尚无真实版本、明确切换演示模式或两份真实版本均不可恢复时使用。
- 开发环境每天凌晨 3 点自动同步；同步失败不清空已经成功保存的两份真实资料版本。
- 首次回填完成后，用户翻页、搜索和筛选均只查询本地完整目录，不因用户请求直接访问 Provider；Provider 是否支持近一年范围、上映日期和分页/游标，必须在实现前实测确认。
