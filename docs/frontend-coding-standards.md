# 妙语购票前端编码规范

> 版本：V1.0  
> 适用范围：妙语购票用户端、移动 H5、管理端及其公共前端模块。  
> 编写依据：[前端应用系统设计](前端应用系统设计.md) V2.4、[妙语购票_前端系统分析设计](妙语购票_前端系统分析设计.md)。

## 1. 目的和规则级别

本文把前端系分中的架构、接口、安全、状态恢复和验收要求落成日常编码规则。开发、联调和评审均以本文为准；接口字段、状态和权限以对应的系统设计文档及后端接口定义为准。

- **必须**：不满足会影响安全、交易正确性、跨端一致性或联调，合并前必须修正。
- **推荐**：没有特殊原因时应遵守；例外要在评审中说明原因。
- **参考**：用于同类问题的设计取舍，不作为合并条件。

## 2. 工程结构和依赖边界

### 2.1 必须：按分层放置代码

前端目录按以下职责组织：

```text
src/
├── app/          Provider、运行时配置、路由守卫、错误边界
├── layouts/      UserLayout、AdminLayout
├── pages/        Umi 路由页面，只负责页面编排
├── modules/      auth/content/agent/ticketing/order/travel/profile/admin
├── features/     agent-workspace/dynamic-cards/seat-map/payment-status
├── shared/       api/components/hooks/types/utils
└── styles/       主题变量和全局基础样式
```

- `pages` 只处理路由参数、页面组合和流程编排，不直接发送网络请求。
- `modules` 负责本模块查询、写操作和状态规则；不得读取其他模块的私有状态。
- `features` 只实现可复用的复杂业务组件，例如座位图、动态卡片、支付状态；不得重建模块接口逻辑。
- 跨模块协作只通过路由、后端业务 ID 和公开 DTO；不得通过全局变量、页面实例或临时缓存传递业务对象。
- 所有普通 REST 请求走唯一的公共 `fetch` REST 客户端；Agent 流式消息使用公共 SSE 客户端。

### 2.2 必须：双端共享业务逻辑，允许视图不同

- PC 用户端和管理端使用 Ant Design；移动 C 端使用 antd-mobile。
- 路由、DTO、请求层、查询缓存、领域 Hook 和错误映射必须共用。
- 桌面端与移动端可以按交互差异拆分 `DesktopView`、`MobileView`，不得复制两套接口调用和状态恢复代码。
- 小于 `1024px` 使用移动单列、底部导航和全屏或抽屉式 Agent；大于等于 `1024px` 使用 PC 左导航、主内容和可选右侧 Agent 区域。
- 移动端优先使用 antd-mobile 的 `NavBar`、`TabBar`、`Popup`、`Dialog`、`Picker`、`Toast`、`Skeleton`、`Empty`、`ErrorBlock`，不重复封装这些已有通用能力。
- 自定义业务组件仅限座位图、Agent 动态卡片、订单与支付恢复等组件；触控目标不小于 44px。

## 3. TypeScript、DTO 和数据格式

### 3.1 必须：接口数据先定义类型再使用

- 每个 REST 请求、SSE 事件、动态卡片和路由参数都必须有明确 DTO 或类型定义。
- 模块对外只暴露公开 DTO；组件不能依赖后端响应中未声明的字段。
- 服务端返回的状态、金额、时间和 ID 不得在页面中自行猜测或重组。
- 对不可信输入，包括 URL 参数、表单、Agent 消息和接口返回的可选字段，必须先校验再渲染或提交。
- 不使用 `any`、`@ts-ignore`、非空断言来跳过类型和空值处理；未知数据使用 `unknown` 并通过校验转换。

### 3.2 必须：统一基础数据格式

- 所有业务 ID 使用 `string` 保存和传递。
- JSON、SSE 和动态卡片中的金额均为两位小数字符串；展示和计算按统一金额工具处理，不使用浮点数直接比较金额。
- 时间使用 ISO 8601 字符串；页面按统一格式化规则展示，不能由页面各自拼接日期字符串。
- Agent SSE 的 `eventId` 是十进制字符串。不得转为 JavaScript `number`，不得用数值比较替代字符串游标规则。
- 可分享的筛选、分页和业务 ID 放入 URL；凭据、精确位置、密码、验证码和前端推断的业务结论不得放入 URL。

### 3.3 推荐：命名能表达状态和动作

- 布尔状态用 `is`、`has`、`can`、`should` 开头，例如 `isSubmitting`、`hasPermission`。
- 用户交互处理函数用 `handle` 开头，例如 `handleConfirmSeat`。
- 查询函数使用 `query`、`load`、`fetch`，写操作使用 `create`、`confirm`、`cancel`、`refund` 等业务动词。
- 不使用 `data`、`result`、`temp` 作为跨模块核心对象名称；必须体现影片、场次、订单、运行或路线等业务含义。

## 4. F2E Spec 详细编码规则

本章采用 F2E Spec 的 HTML、CSS、JavaScript、React、TypeScript 和 Git 规则，并按本项目技术边界取用。本文第 2、3、5 至 12 章的项目规则优先级更高。

### 4.1 通用格式

**必须**：

- 所有源文件和 Markdown 使用 UTF-8 编码、LF 换行、2 个空格缩进；不使用 Tab。
- 文件末尾保留一个换行；删除行尾空格；不提交无关的整文件格式化。
- 单行超过 100 个字符时应合理换行；JSX 属性、对象、数组和函数参数较长时每项单独一行。
- 代码块、条件分支、函数、类、接口等左大括号前保留一个空格，右大括号独占一行。
- 注释应说明业务原因、边界或限制，不重复翻译代码本身；注释符和正文之间保留一个空格。

### 4.2 HTML 与 JSX

**必须**：

- 使用语义标签表达页面区域：`header`、`nav`、`main`、`section`、`article`、`button`、`form`。禁止用点击 `div` 模拟按钮或链接。
- 页面只有一个主标题 `h1`，子标题按 `h2`、`h3` 顺序递进；不要为了字号跳过标题层级。
- 跳转使用 `Link` 或 `a`，触发提交、打开弹窗、切换状态等动作使用 `button`。
- 图片提供有意义的 `alt`；纯装饰图片使用空 `alt`。表单字段有可见 `label` 或正确的无障碍名称。
- 标签和属性使用 JSX 标准写法：属性名使用 `className`、`htmlFor` 等 React 属性，字符串属性使用双引号，布尔属性传布尔值而不是字符串。
- 外部链接新窗口打开时加 `rel="noreferrer"`；链接地址必须经过白名单校验。
- 禁止 `dangerouslySetInnerHTML` 直接渲染用户、接口或 Agent 提供的内容。确需富文本时，先经过白名单净化。

**推荐**：

- 一个组件的 JSX 层级过深时，拆成语义明确的子组件；不要用大量无含义的嵌套容器凑布局。
- 交互元素应支持键盘聚焦与操作，不能只依赖鼠标或触摸。

### 4.3 CSS

**必须**：

- 每个声明以分号结尾；属性名与冒号之间不留空格，冒号后保留一个空格。
- 选择器与 `{` 之间保留一个空格；`>`、`+`、`~` 等组合器两侧保留一个空格；逗号分隔值的逗号后保留一个空格。
- 一条声明独占一行，右大括号独占一行；CSS 注释写作 `/* 注释 */`。
- 属性选择器和属性值使用双引号，例如 `[type="button"]`。
- 选择器使用小写 `kebab-case`；不使用 ID 选择器；不用标签名叠加多层后代选择器限制组件样式。
- 禁止无说明的 `!important`。第三方组件兼容确实需要时，仅在集中兼容样式中使用，并写明原因、组件和版本范围。
- 页面布局使用 CSS，不使用 HTML 属性或 JSX 内联样式控制样式。

**推荐**：

- 样式属性按“定位与布局、盒模型、文字、视觉、动画”分组，组之间留一个空行。
- 避免超过 3 层的后代选择器，避免依赖 DOM 层级；优先为组件元素定义明确类名。
- 颜色、间距、字号、圆角、阴影统一使用主题变量；同一业务状态使用同一个修饰类，例如 `--selected`、`--disabled`、`--error`。

### 4.4 JavaScript 与 TypeScript 书写

**必须**：

- 变量、属性、函数使用 `camelCase`；组件、类型、接口、枚举使用 `PascalCase`；常量名称以业务语义为先，不使用单字母和难懂缩写。
- 使用 `const`，仅在变量必须重新赋值时使用 `let`；禁止 `var`。
- 使用 `===`、`!==`，禁止 `==`、`!=`；禁止依赖隐式类型转换。
- 字符串使用单引号，模板拼接使用模板字符串；不要通过 `+` 拼接复杂文本、URL 或 HTML。
- 对象和数组字面量末尾保留逗号；对象属性简写和解构在能提升可读性时使用。
- 禁止修改函数参数、props 和已有 state；更新对象或数组时创建新引用。
- 条件判断必须明确：不要把数字、空字符串或对象的真假值当作业务状态；例如数量展示使用 `count > 0`。
- `switch` 必须有 `default` 分支或在穷尽检查中明确抛出错误。
- 每个异步调用处理成功、失败和 finally 清理；Promise 不得悬空。
- 不使用 `eval`、`new Function`、动态脚本加载或根据服务端字符串调用函数。

**推荐**：

- 单个函数只完成一个清楚动作；分支复杂、超过一个屏幕时拆成命名函数或 Hook。
- 参数超过 3 个或含义易混淆时使用对象参数，并定义参数类型。
- 公共工具函数不读取页面状态、不操作 DOM、不发请求，保持输入输出可预测。

### 4.5 React 与 Hooks

**必须**：

- 函数组件和自定义 Hook 名称使用 `PascalCase` 与 `use` 前缀；组件只接收明确类型的 props。
- Hook 只能在函数组件或自定义 Hook 顶层调用，不能放在条件、循环、回调或普通函数中。
- `useEffect` 使用到的外部依赖必须写入依赖数组；定时器、订阅、请求取消器和 SSE 连接必须在清理函数中释放。
- 列表 `key` 必须稳定唯一；不能使用随机数、当前时间或会变动列表的下标。
- 受控表单值、提交状态、错误提示和禁用状态保持一致；提交中不得允许第二次提交。
- 不在 render 中发送请求、修改全局状态或读写本地持久存储等副作用。
- `useMemo`、`useCallback`、`memo` 只用于已确认的重复计算或渲染问题，不能机械使用。

**推荐**：

- 页面组件超过一个主要职责时，拆分展示组件、表单组件和业务 Hook；展示组件优先保持无请求副作用。
- 多处使用的状态机、格式化、权限判断和错误映射提取到公共 Hook 或模块工具中，避免不同页面各自实现。

### 4.6 Git 提交

**必须**：

- 一个提交只包含一类可说明、可回退的修改；不要把功能、重构、依赖升级和整库格式化混在同一个提交中。
- 提交前检查差异，禁止提交 `.env`、Token、Cookie、账号、构建产物、`node_modules` 和本地调试文件。
- `package.json` 变更依赖时，锁文件必须同步提交；纯安装造成的无关锁文件变化不提交。
- 不改写他人已推送的公共分支历史；解决冲突后重新执行相关检查。

**推荐**：

- 使用约定式提交格式：`<类型>(<范围>): <描述>`。
- 类型使用 `feat`、`fix`、`docs`、`refactor`、`style`、`test`、`chore`；范围写 `auth`、`agent`、`ticketing`、`order`、`travel`、`admin` 等模块名。
- 提交描述使用团队通用中文，动词开头并说明实际修改，例如 `fix(order): 修复支付结果恢复后页面未刷新`。

### 4.7 注释规范

注释的目标是说明代码本身看不出来的业务原因、约束和后果。变量名、函数名和组件名先写清楚；不能用注释弥补模糊命名或过长函数。

**必须：以下位置写中文业务注释或 JSDoc。**

| 位置 | 注释至少说明什么 |
| --- | --- |
| 模块对外 API、公共 Hook、公共组件 | 用途、关键入参和返回值、调用方必须遵守的限制 |
| 订单、支付、退票、同步等写操作 | 幂等标识来源、允许状态、结果未知时为何只能查询 |
| SSE 连接和恢复 | `runId`、`lastEventId`、`planVersion` 的作用，断流后恢复顺序，禁止重发什么 |
| 认证、权限和隐私处理 | 为什么清缓存、为什么不保存某字段、后端仍需校验的范围 |
| 竞态控制、缓存失效、请求取消 | 要丢弃哪类旧响应，以及不处理会造成什么页面错误 |
| 复杂映射、状态机、计算或正则 | 输入条件、关键分支和输出边界 |
| 临时兼容、第三方组件覆盖或 `!important` | 兼容对象、原因、影响范围和计划删除条件 |
| TODO/FIXME | 具体问题、影响、负责人或关联需求编号；没有处理计划不得保留 |

**推荐的写法：**

```ts
/**
 * 查询原建单结果，不重新创建订单。
 *
 * 建单响应丢失时，服务端可能已锁座并创建订单；重发会产生重复订单，
 * 因此必须沿用 clientRequestId 查询服务端状态。
 */
async function recoverCreatedOrder(clientRequestId: string): Promise<OrderSnapshot> {
  return queryOrderByRequestId(clientRequestId);
}

// 用户切换影院后，旧影院的场次响应不能覆盖当前页面。
// 取消请求可节省网络；请求完成先后不确定时仍需用 queryKey 二次判断。
function shouldApplyShowsResponse(queryKey: string, currentQueryKey: string): boolean {
  return queryKey === currentQueryKey;
}
```

**不要这样写：**

```ts
// 查询订单
const order = await queryOrder(orderNo);

// TODO: 后面优化
const result = await submitPayment(payload);
```

- 第一条只是重复函数名，删除即可。
- 第二条没有问题、影响和处理计划，无法安排和验收。

**JSDoc 要求：**

- `shared/` 中公开的函数、Hook、组件和类型必须有 JSDoc；模块内只被一处调用的简单函数不强制。
- JSDoc 第一行用一句话说明用途；涉及状态限制、安全限制、异常恢复或副作用时，继续写清楚。
- 参数和返回值名称已经能表达含义时，不机械重复 `@param`、`@returns`；含义、单位、格式或可空条件不明确时必须补充。
- 组件的 props 类型优先写在类型字段注释中；说明“何时传、传错会怎样”，而不是重复字段名。

**维护要求：**

- 修改逻辑、接口、状态或权限时，同步修改附近相关注释；注释与代码冲突时，以代码修正为优先，提交前必须删改过期注释。
- 不提交大段被注释掉的旧代码。需要保留历史用 Git 查看；确需灰度或临时禁用时，保留最小代码并说明开关、恢复条件和删除时间。
- 不在注释中写密码、Token、验证码、完整用户输入、精确位置或其他敏感数据。
- 注释使用自然中文，标点和术语与本文保持一致；代码标识、接口路径、DTO 字段和枚举值保持原样。

## 5. 样式和组件编码

### 5.1 必须：自定义样式只写 CSS 文件

- 禁止 JSX `style` 属性、样式对象和 CSS-in-JS，包括 `styled-components`、Emotion。
- 全局变量和基础样式放在 `styles/`；业务组件样式与组件放在同一目录，通过 `className` 关联。
- 外观切换使用语义清楚的 CSS 类名，例如 `seat seat--selected`，不得在 TSX 中写颜色、间距和尺寸。
- 自定义类名使用语义化 `kebab-case`，例如 `order-summary`、`agent-progress`；禁止 `box1`、`red`、`left` 等无业务含义的命名。
- 可复用色值、间距、圆角和字号通过主题变量管理，不在多个组件中复制硬编码值。
- 不直接依赖或大范围覆盖 Ant Design、antd-mobile 的内部样式类；确需兼容时，应集中处理并注明原因和影响组件。

### 5.2 必须：组件职责清楚且可恢复

- 应用壳层负责认证检查、网络提示、路由守卫和错误边界。
- 布局层只管理导航和布局，不直接调用业务接口。
- 页面层只组合模块和功能组件；领域模块负责查询缓存、领域操作与接口调用。
- 应用壳层和页面内容区分别设置错误边界。局部组件渲染失败时不能导致全站白屏。
- 列表使用稳定的服务端 ID 作为 `key`；会排序、插入或删除的列表不能使用数组下标。
- 加载、空数据、刷新中、失败、无权限和资源不存在必须有明确组件状态，不能只留空白区域。

### 5.3 推荐：关注大列表和首屏性能

- Agent 长会话使用分段或虚拟渲染，座位图只做局部更新。
- 搜索输入做防抖；无依赖查询并行发起；筛选条件变化时取消失效请求，避免旧响应覆盖新数据。
- Agent、地图、管理端、交易页按路由拆包，不进入公开首页首屏包。
- 海报和非首屏卡片延迟加载，图片固定尺寸并提供加载失败占位。

## 6. 请求、缓存和状态处理

### 6.1 必须：请求和会话统一管理

- 所有普通 REST 请求统一由公共请求层发送，并携带 `credentials: 'include'`。
- 前端不读取、保存、打印或拼接 Cookie、JWT、验证码、模拟支付密码。
- `401` 时只执行一次会话清理和登录跳转，同时关闭 SSE、清除私有缓存并保留安全回跳地址。
- `403` 显示无权限页面或区域，不循环跳转登录。
- 根据 HTTP 状态和接口错误码决定页面分支，不能依赖错误文案文字判断。
- 写操作完成后使相关查询缓存失效并重新查询；不得直接把本地对象改成“成功结果”。

### 6.2 必须：状态按所有权保存

| 状态类别 | 保存位置 | 规则 |
| --- | --- | --- |
| 认证与壳层 | 全局运行时状态 | 只保存身份、角色、网络提示；以 `/auth/me` 结果为准 |
| Agent 活跃连接 | Agent 全局状态 | 只保存 `sessionId`、`runId`、`planVersion`、`lastEventId` 等恢复摘要 |
| 可分享导航 | URL | 只保存筛选、分页和业务 ID，不保存敏感信息 |
| 影片、座位、订单、支付、出行 | 请求缓存 | 服务端快照；写后失效并重新查询 |
| 表单、弹窗、临时选座 | 页面局部状态 | 随页面退出清理；敏感输入不持久化 |

### 6.3 必须：查询竞态和异常按统一规则处理

| 场景 | 页面处理 | 后续动作 |
| --- | --- | --- |
| 首次加载 | `Skeleton` 或页面级加载状态 | 等待或允许离开 |
| 有旧数据刷新 | 保留旧数据并显示局部加载 | 新结果替换旧快照 |
| 空数据 | `Empty` 和调整筛选或创建入口 | 用户主动调整 |
| 404 | 资源不存在提示 | 返回对应列表 |
| 409 | 状态已变化提示 | 重新查询服务端资源，由用户重新决定 |
| 422 | 字段或业务校验提示 | 保留非敏感输入 |
| 网络或 5xx | 保留上下文和 `traceId` | 只读查询可重试，写操作只查结果 |
| 离线 | 全局离线提示，已加载内容标为只读快照 | 禁止锁座、下单、支付和退票 |

- 历史快照只存在当前页面内存；本期不建设 Service Worker 和持久离线业务缓存。
- 影片、影院可以浏览快照；天气和交通必须标记为“待校验”；订单和电子票必须联网确认后才能操作；座位图快照失效后禁止锁座和下单。

## 7. 关键写操作和交易规则

### 7.1 必须：所有关键写操作都有结果未知状态

关键写操作统一使用 `READY → SUBMITTING → SUCCEEDED / FAILED / RESULT_UNKNOWN` 状态。

- `SUBMITTING` 和 `RESULT_UNKNOWN` 时禁止重复点击。
- 网络中断、刷新或响应丢失时，不能直接显示失败，也不能再次创建、支付、取消或退票。
- 必须使用原来的业务 ID 或幂等标识查询服务端结果，再按查询结果更新页面。
- 只有服务端明确终态后，按钮才恢复可操作或进入下一步。

### 7.2 必须：购票和支付不信任前端旧数据

- 场次页只在已知 `movieId` 和 `cinemaId` 时查询；兜底跳转保留两者：`/shows?movieId={movieId}&cinemaId={cinemaId}`。
- 已有 `showId` 直达选座前，必须确认场次存在且 `status = ON_SALE`；停售、参数缺失或多个场次未选择时，回到正确的筛选或场次页。
- 建单以 `seatIds` 和 `clientRequestId` 提交。收到 `409` 时刷新座位并只保留仍可选座位，不能把本地选座显示为已锁定。
- 支付完成、取消、退票或同步接口响应丢失时，只查询结果；不得自动重发写请求。
- 建单、退票等确认仅提交服务端下发的 `actionId` 和 `confirmed`，不得由前端重组金额、座位和订单字段。
- `RESULT_UNKNOWN` 只查询原操作状态，不生成新的幂等键。

## 8. Agent SSE 和动态卡片

### 8.1 必须：使用可恢复的 fetch 型 SSE 客户端

- Agent SSE 是携带 JSON 请求体、Cookie 和 `Last-Event-ID` 的 POST 流；禁止用只支持 GET 的原生 `EventSource` 代替。
- 使用 `fetch` 和 `AbortController` 管理连接；组件卸载、切换会话、登出时必须关闭连接。
- 同一 Agent 工作区只允许一条活动连接。
- 断流或 20 秒无事件时，先按原 `runId` 查询状态，再按 `lastEventId` 续传；服务端返回 `stream.reset` 时，拉取消息与运行快照后一次替换视图。
- 恢复过程禁止重发用户消息、已确认动作或任何写操作。
- 收到旧 `planVersion` 的事件必须忽略，不能覆盖已展示的新计划和用户已选方案。

### 8.2 必须：Agent 输出一律按不可信内容处理

- 只渲染协议白名单内的结构化消息和动态卡片；未知消息类型降级成安全文本或安全占位。
- 不渲染 Agent 输出中的脚本、HTML、任意 URL 和指令为可执行前端行为。
- “忽略规则”“泄露提示词”“执行脚本”等文本只作为普通内容显示，不能触发工具调用。
- 普通用户不展示原始计划图；管理端轨迹只展示脱敏参数、摘要、依赖和失败原因，不展示密码、Token、精确位置、完整用户输入或模型内部思维过程。
- Agent 不可用时保留已完成内容，并提供影片、影院等固定页面入口，基础购票流程不能被阻断。

## 9. 权限、隐私和页面安全

### 9.1 必须：前端显示不等于权限校验

- 管理页面和按钮按后端权限结果显示；真正的用户订单、会话、画像和管理操作必须依赖后端再次鉴权。
- 管理路由在加载业务数据前校验管理员角色；普通用户访问管理端显示拒绝页面。
- 外部链接使用白名单和安全打开方式；用户输入与服务端富文本必须转义。
- 埋点、日志和错误上报不得记录 Token、密码、验证码、模拟支付密码、完整 Agent 输入、精确位置或完整个人信息。

### 9.2 必须：位置权限按用户操作申请

- 位置不是购票前置条件，只在用户点击“路线规划”或“使用当前位置”后申请。
- 权限为 `granted` 时获取位置；`prompt` 时先展示用途和第三方共享说明，再触发浏览器授权；`denied` 时不调用定位接口，改为设置引导和手动地点。
- 浏览器原生授权弹窗不能被项目自定义弹窗替代或覆盖。
- 精确坐标仅存于当前出行流程内存，离开页面或登出后清除；不得写入 URL、埋点或普通本地存储。
- 向第三方地图发送位置前，明确说明接收方、用途和数据类型；用户不同意时允许手动地点，不发路线请求。
- 不在首页自动申请位置或通知权限；本期观影提醒使用邮件，不申请浏览器通知权限。

### 9.3 必须：用户权利有明确入口

- 注册页隐私协议链接可阅读，同意框默认未勾选；不同意不得注册，但仍可浏览公开影片。
- 个人中心提供清除 Agent 会话、撤回可选偏好和退出登录入口。
- 浏览器权限由用户在浏览器或系统设置中撤回，页面提供清楚说明；不得伪造“已撤回系统权限”的状态。

## 10. 性能和验收要求

### 10.1 必须：满足页面性能基线

| 项目 | 目标 | 编码要求 |
| --- | --- | --- |
| 核心首屏可操作 | 不超过 2.5 秒 | 优先渲染壳层与核心入口，非首屏资源延迟加载 |
| Agent 请求受理 | 1 秒内显示 `runId` 或首个进度 | 未收到前显示连接状态，禁止重复提交消息 |
| Agent 首个有效结果 | P90 不超过 5 秒 | 持续展示节点和取消入口 |
| 简单/复杂 Agent 任务 | P90 10 秒/20 秒内有结果或阶段状态 | 保留已完成卡片，展示重规划或降级 |
| SSE 无事件 | 20 秒 | 查询原 `runId` 后按事件游标恢复 |
| 首页初始 JS/CSS | gzip 后不超过 450KB/100KB | 通过路由拆包和主题变量控制体积 |
| 首屏图片 | 单张 WebP/AVIF 不超过 200KB | 固定尺寸、响应式图片、失败占位 |

### 10.2 必须：合并前覆盖关键验收场景

- 游客浏览后登录，并回到原流程；用户和管理员权限路由正确。
- PC 与移动端均能完成方案、选座、订单、模拟支付、电子票、出行和退票主流程。
- 建单、支付、取消、退票和同步响应丢失后，均能查询原结果且不重复写入。
- 座位冲突、Agent 断流、SSE 重连、计划重规划、弱网、离线快照、定位拒绝和地图失败均有明确降级。
- Agent 未知消息、恶意富文本和疑似提示注入内容均只会安全展示，不执行脚本或请求。
- 构建使用发布配置；Chrome Lighthouse 移动模式、4 倍 CPU 降速、Slow 4G、清空缓存，每个核心页面至少测量 5 次并取中位数；答辩 PC 与手机各完成一次真实流程。
