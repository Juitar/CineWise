### 0.3 执行原则

1. “必须”项是代码评审和交付门槛；违反时必须修改，或按第 10 节登记有期限的例外。
2. 本规范定义代码如何实现，PRD和系统设计定义实现什么。接口、状态、字段、错误码或职责不明确时，先补契约再编码。
3. 示例用于说明约束，不是可复制的完整实现；事务、权限、幂等和错误映射必须结合所属用例补齐。
4. 规范中的“合并”包括合入共享分支、交付集成包或关闭实现任务，不以是否使用 Pull Request 为前提。

## 1. 团队协作规则

### 1.1 模块边界（必须）

1. 采用模块化单体；不得为了“解耦”拆出独立服务、工作流引擎或重复认证体系。
2. Agent、Controller、定时任务和事件监听器只能调用 Application Service；不得直接操作 Repository、座位、订单、支付或退款表。
3. 票务交易模块是场次、座位、订单、支付、电子票和退款状态的最终可信来源。Agent 不得绕过票务 Application Service 写交易数据。
4. 当前用户身份只能从 Spring Security 上下文获得；禁止信任请求体、查询参数或 Agent 参数中的 `userId`、`role`、金额和订单状态。
5. 第三方内容、天气、地图等访问必须经各自的 Adapter；Adapter 要返回统一的内部 DTO、数据来源和更新时间，并提供 Mock/降级实现。
6. 跨模块调用只依赖公开 Application API、DTO 或事件；不得 import 对方的 persistence/entity/repository 包。

### 1.2 负责人和变更责任（必须）

| 范围 | 最终负责人 | 变更前须同步 |
| --- | --- | --- |
| 票务交易、订单状态、座位、支付、退款、交易工具 | A | B、C、D（若影响其契约） |
| Agent 计划、工具协议、确认机制、SSE 轨迹 | B | A、C、D |
| 认证、安全上下文、JWT Cookie、权限 | C | A、B、D |
| 外部数据、用户画像、推荐、出行、质量回归 | D | A、B、C |
| 公共响应、错误码、OpenAPI、基础设施 | 对应模块负责人 | 全组 |

修改已冻结接口、DTO 字段、枚举、状态机、数据库表或公共错误码时，必须先在对应变更记录中说明影响范围，并同步更新契约文档与 Mock。未经负责人确认，禁止破坏兼容性。

### 1.3 变更记录与交付（必须）

当前仓库尚未建立 OpenSpec 目录或工具链，因此不得把 OpenSpec 当作已经落地的强制依赖。每项实现至少要有可追踪的变更记录；后续若团队正式引入 OpenSpec，可直接用 OpenSpec change 承载以下内容。

1. 新功能、缺陷修复、接口/数据/状态变更开始前，建立变更单，写明编号、背景、范围、非范围、验收标准、负责人和受影响模块。变更单可以是任务文档、Issue 或团队确认的等价载体。
2. 涉及接口、DTO、状态机、数据库表、公共错误码或跨模块依赖时，变更单必须包含契约增量和可执行任务清单；受影响模块负责人先确认契约，再开始实现。
3. 每个实现任务必须可独立验证并记录验证命令、结果和关联提交；不得把无关重构、全库格式化或临时调试混入同一变更。
4. 提交信息使用语义化格式，例如 `feat(ticket): 原子建单`、`fix(auth): 原子消费验证码`、`test(agent): 覆盖确认凭证过期`，并引用变更编号。
5. 每个模块至少由另一名成员审查一次；跨模块变更由受影响模块负责人确认。评审依据是冻结契约、变更单验收标准和本规范。
6. 变更关闭前必须通过构建、相关测试和第 9 节检查；实现导致契约变化时，同步更新系统设计、OpenAPI、Mock 和调用方。

## 2. 工程与代码结构

### 2.1 包结构（必须）

每个业务模块按职责组织，推荐结构如下：

```text
<module>/
  api/             # Controller、请求/响应 DTO
  application/     # 用例编排、事务边界、对外 Application API
  domain/          # 领域模型、值对象、状态枚举、领域规则
  infrastructure/  # Repository 实现、第三方 Adapter、缓存、消息/任务实现
```

- `api` 只完成认证、参数校验、调用应用服务和映射响应，不承载业务判断或事务。
- `application` 是写操作和跨聚合流程的唯一入口；事务优先定义在此层。
- `domain` 不依赖 Spring MVC、HTTP DTO、JPA/MyBatis Entity 或第三方 SDK。
- `infrastructure` 只实现存储、缓存、外部调用等技术细节，不能决定业务状态流转。

### 2.2 命名与对象边界（必须）

1. 包名小写；类使用 UpperCamelCase，方法和变量使用 lowerCamelCase；常量使用 `UPPER_SNAKE_CASE`。
2. 类型后缀统一：HTTP 入参 `*Request`，HTTP 出参 `*Response`，查询条件 `*Query`，持久化实体 `*Entity`，内部传输对象 `*DTO`。禁止 `UserVO`、`UserDTO`、`UserDO` 在同一边界混用。
3. Controller 不返回 Entity；Repository 不接收 HTTP Request；Agent Tool 不暴露数据库实体。
4. Boolean 以语义命名，如 `enabled`、`paid`，不声明字段 `isPaid`；数据库列可用 `is_paid`，MyBatis 中必须显式映射为 Java 属性 `paid`。
5. 枚举用稳定业务词汇，例如 `PENDING_PAYMENT`、`PAID`；不得让前端、数据库和接口使用不同的同义状态。
6. 禁止魔法值；超时时间、限流阈值、锁座分钟数使用配置项或有语义的常量。

### 2.3 格式、导入与注释（必须）

以下规则参考同目录的《aliyun后端编码规范》，并作为本项目代码审查基线。

1. 源文件使用 UTF-8、LF 和 4 个空格缩进，不使用 Tab；单行不超过 120 字符，超长表达式在运算符、逗号或方法链处换行并保持一致缩进。
2. 左大括号不换行；非空代码块的大括号内各自换行；`if/for/while/switch` 与左括号间有一个空格；逗号后、二元/三元运算符两侧各有一个空格。
3. 使用一个空行分隔不同逻辑段，不用多余空行或为了对齐变量而插入多个空格。
4. import 禁止通配符导入；删除未使用导入；静态导入仅用于明显提升可读性的常量或断言。
5. 类、公开方法、复杂业务规则、状态迁移、并发控制和非常规取舍必须有中文注释，说明“为什么”和约束，不逐行翻译显而易见的代码。
6. `TODO` 必须写明责任人或任务编号及预期处理条件；禁止提交无归属的 TODO、已失效注释和被注释掉的废弃代码。

### 2.4 Java 编码规则（必须）

1. 名称不得以 `_` 或 `$` 开头或结尾；不得使用拼音、中文或含义不清的缩写。循环下标等极小作用域变量可使用 `i`、`j`。
2. 类名使用名词；抽象基类以 `Abstract` 或 `Base` 开头；异常类以 `Exception` 结尾；测试类以被测类名开头、`Test` 结尾。
3. 方法名应表达动作：查单个对象使用 `get`，查列表使用 `list`，统计使用 `count`，新增使用 `create`/`save`，删除使用 `remove`，更新使用 `update`。布尔判断方法使用 `is`/`has`/`can`。
4. 禁止裸字面量：业务状态、缓存 Key 前缀、超时、分页上限、错误码等使用枚举、配置或语义明确的常量。`long` 字面量使用大写 `L`。
5. 只读常量使用 `private static final` 并就近定义；跨模块共享常量必须确有稳定语义，禁止建立万能 `Constants` 类。
6. 覆盖接口或父类方法必须标注 `@Override`；接口变更不得直接破坏调用方，应新增兼容接口或走明确的废弃/迁移流程。
7. `equals` 由常量或 `Objects.equals` 调用；包装类型比较使用 `equals`；浮点数不以 `==` 判断；金额、票价和计算金额只使用 `BigDecimal`。
8. 禁止返回 `null` 集合；集合为空时返回空集合。对外 DTO 中可空字段必须在契约中说明，不能依靠调用方猜测。
9. 不使用 `Object`、原始类型集合或 `Map<String, Object>` 代替业务模型；确需动态字段时封装专用类型并在 OpenAPI/工具 Schema 中声明。
10. 资源使用 `try-with-resources` 自动关闭；禁止在 finally 中以可能抛异常的清理操作掩盖原始异常。
11. Controller、Application Service、Repository、Adapter 和 Job 的方法应短小并只承担单一职责；出现多层嵌套条件时优先使用守卫语句、提取方法或状态机，不以“万能工具类”堆积逻辑。

### 2.5 集合、并发与控制流（必须）

1. 集合转数组使用 `collection.toArray(new Type[0])`；数组转集合后得到的定长列表不得执行新增/删除操作，需要可变集合时重新构造 `new ArrayList<>(...)`。
2. 遍历集合时不得调用集合自身的 `remove`；需要删除时使用 `Iterator.remove()` 或先收集待删除项后统一处理。
3. 禁止在 foreach 内修改被遍历集合；禁止以并发容器掩盖错误的业务并发设计。
4. 禁止直接创建无界线程池、无界队列或在请求中随意 `new Thread()`；异步任务使用统一线程池并配置线程名、队列上限、拒绝策略和监控。
5. 共享可变状态必须明确同步策略。票务库存、座位、支付和退款以数据库条件更新、唯一约束和事务为准，不能仅依赖 JVM 锁或 Redis 锁。
6. 条件分支必须完整覆盖枚举状态；`switch` 必须处理 `default` 或显式穷举。禁止空的 `catch`、空的 `if` 分支和依靠异常控制正常流程。
7. 分页、批处理、`IN` 查询和导出必须限制数据规模；`IN` 条件超过 1000 项时分批或改用合适的关联查询。

### 2.6 异常与日志（必须）

1. 业务可预期异常使用明确业务异常和错误码；基础设施异常在边界处转换为领域可理解的错误，不将数据库/SDK 异常原样暴露给前端。
2. 同一异常只在能够处理、补充关键上下文或最终统一出口处记录一次，避免层层重复打印堆栈。记录异常时保留原始 `cause`。
3. 日志使用参数化写法，例如 `log.warn("order create failed, orderId={}", orderId, e)`；禁止字符串拼接产生无效开销或丢失堆栈。
4. 日志不得打印密码、验证码、JWT、Cookie、身份证明、完整手机号/邮箱、支付密码和密钥。需要定位时记录 `traceId`、内部 ID、脱敏摘要和错误码。
5. `debug` 用于开发诊断，`info` 记录关键正常业务节点，`warn` 记录可恢复风险，`error` 记录需要处理的失败；禁止用 `System.out.println`。

### 2.7 通用代码质量（必须）

1. 不捕获后吞掉异常；捕获时要么转换为有业务语义的异常，要么记录足够上下文后继续抛出。
2. 禁止 `SELECT *`、字符串拼接 SQL 和无限制列表查询。分页接口必须限制 pageSize 上限。
3. 不以 `Map<String, Object>` 传递业务对象或跨模块契约；确有动态扩展字段时，必须在接口文档明确键和值语义。

### 2.8 Maven、依赖与自动检查（必须）

1. 使用 Maven Wrapper 固化 Maven 入口；开发机和 CI 统一执行 `./mvnw clean verify`（Windows 使用 `mvnw.cmd clean verify`），不得以 IDE 中“可以运行”替代构建结果。
2. Java 版本统一为 21；依赖版本在父 POM 的 `dependencyManagement` 或 Spring Boot BOM 中集中管理，子模块不得重复声明同一依赖的不同版本。
3. 禁止动态版本、`LATEST`、无评估的 `SNAPSHOT` 和重复引入同功能库。新增或升级依赖必须记录用途，执行 `dependency:tree` 检查冲突，并检查已知高危漏洞。
4. 后端骨架建立时必须接入统一格式与静态检查插件，并在 `verify` 阶段执行。团队可在 Spotless/Checkstyle 中选择一种格式门禁，并使用 SpotBugs 或等价检查发现空指针、资源泄漏和错误并发用法；规则配置由父 POM 唯一维护。
5. 自动格式化只作用于本次修改文件；禁止在业务变更中顺带格式化全库。生成代码、迁移脚本和第三方文件按插件排除清单处理。
6. 编译告警、新增静态检查告警和测试失败不得通过跳过参数掩盖。确属误报时，在变更记录中写明规则、原因和最小范围抑制，不允许全局关闭。

### 2.9 Spring 与 MyBatis 实现规则（必须）

1. Spring Bean 使用构造器注入，依赖字段声明为 `final`；禁止字段注入。Bean 默认必须无共享可变业务状态，请求、用户和任务上下文不得保存在单例字段中。
2. 配置项按业务前缀集中到 `@ConfigurationProperties`，配合 Bean Validation 校验必填项和范围；禁止在业务类中散落大量 `@Value`，禁止为缺失的密钥提供看似可用的生产默认值。
3. 不为每个类机械创建 `Service + ServiceImpl`。只有存在多个实现、稳定跨模块能力或需要隔离基础设施时才抽接口；接口放在调用方可依赖的公开边界，实现类留在所属模块。
4. HTTP DTO、Command、事件等不可变载体优先使用 `record`；MyBatis Entity 只存在于 infrastructure/persistence。禁止对领域对象或 Entity 使用 Lombok `@Data` 自动生成不受控的 `equals/hashCode/toString`。Entity 可按需使用 `@Getter`、`@Setter`、`@NoArgsConstructor`，并手动控制 `equals/hashCode/toString`。
5. 跨层映射默认使用显式手写 Mapper/Assembler；禁止用反射式 `BeanUtils.copyProperties` 掩盖字段语义、金额/时间转换或敏感字段泄漏。若全组统一采用 MapStruct，版本和规则由父 POM 管理，生成实现不提交仓库，金额、时间、枚举和敏感字段必须显式配置；不得由个人模块单独引入。
6. MyBatis-Plus Wrapper 和 Mapper 只能在 infrastructure 层使用；复杂联表、条件更新和性能关键 SQL 使用明确 XML/注解 SQL，并检查影响行数。Application/Domain 层不依赖 MyBatis 类型。
7. `@RestControllerAdvice` 统一完成校验错误、业务异常和未知异常映射；Controller 不自行 `try/catch` 拼响应。业务异常携带稳定错误码，不携带 HTTP、SQL 或数据库实现细节。
8. 线程池、HTTP 客户端、JSON、时钟和事务事件发布器由统一配置提供；禁止业务代码随意 `new` 客户端、线程池或 `ObjectMapper` 形成不同超时和序列化规则。

### 2.10 环境配置（必须）

1. `application.yml` 只保存所有环境共用的非敏感默认值；`application-dev.yml`、`application-test.yml`、`application-demo.yml` 保存对应环境差异。本期不建设配置中心或 Vault。
2. 数据库密码、JWT Secret、大模型及第三方服务密钥通过环境变量或只读 Secret 文件注入，不写入 YAML、数据库、镜像或版本库。
3. 仓库只允许提交 `.env.example` 等无敏感值模板，模板列出变量名、用途和获取方式；真实 `.env` 必须被 Git 忽略。
4. 必需配置缺失或格式非法时启动失败；可选外部能力缺失时只能进入设计允许的 Mock/降级模式，并输出不含密钥值的告警。

## 3. API、错误码与契约

### 3.1 REST 约定（必须）

1. API 统一位于 `/api/v1`；资源路径使用小写复数和连字符，例如 `/orders/{orderNo}`。
2. 除下载、健康检查和 SSE 等明确例外外，统一返回 `Result<T>`；`code` 为数值，成功值为 `0`，错误响应包含稳定的六位数值错误码、用户可读 `message` 和 `traceId`。禁止同一字段一处返回数字、另一处返回字符串。
3. 请求 DTO 必须有 Bean Validation；服务端始终校验，前端校验不能替代后端校验。
4. 分页查询统一使用 `page`、`size`，响应使用 `PageResult<T>`；页码起点、默认值和 `size` 上限在公共配置中唯一声明。排序字段由服务端白名单映射，不接受任意列名。
5. 对“用户自己的资源”先按当前用户过滤再查询；查不到返回 404，不能因 403/不同错误泄露其他用户订单或票是否存在。
6. 前端可见业务 ID 一律序列化为字符串。金额在 Java 中使用 `BigDecimal`、在 JSON 中使用两位小数字符串；Agent 工具和 Agent 卡片时间使用 ISO 8601 UTC `Z`，普通 REST 可返回带偏移时间，但必须表示同一时刻。
7. `orderId` 是内部业务 ID，`orderNo` 是面向用户与 URL 的订单号；不得互换字段名。Repository 可按内部 ID 查询，用户 REST 和 Agent 查询默认使用 `orderNo`，事件按冻结 Schema 使用 `orderId`。

### 3.2 错误码注册规则（必须）

失败响应使用后端系统设计冻结的六位数值 `ABBCCC`，REST JSON 和 Agent `errorCode` 均返回 Number，不返回带连字符的字符串。

| 位置 | 含义 | 已分配值 |
| --- | --- | --- |
| `A` | 错误类别 | `1`协议/通用客户端错误；`2`业务规则错误；`3`外部依赖错误 |
| `BB` | 模块编码 | `00`通用协议、`01`认证、`02`用户画像、`03`内容数据、`04`排期座位、`05`订单支付、`06`Agent、`07`出行、`08`管理 |
| `CCC` | 模块内序号 | 由所属模块负责人顺序登记，`000`不分配 |

1. 公共错误码注册表是唯一编号来源；新增错误码先确认错误类别、模块和 HTTP 状态，再由模块负责人登记，禁止仅在代码中临时定义。
2. 已发布错误码不得更换含义或分配给其他异常。废弃错误码保留登记和说明，不回收复用。
3. HTTP 状态表达请求的协议结果，六位错误码表达稳定业务原因；同一错误码不得根据调用入口映射为相互矛盾的 HTTP 状态。
4. REST、OpenAPI、Agent Tool、前端错误映射和测试必须复用相同数值。例如 `204001` 表示座位不可锁定，`205005` 表示幂等请求参数不一致，`100429` 表示请求过于频繁。
5. `message` 本期使用简洁中文，仅用于展示和诊断；前端、Agent 和测试不得通过匹配 message 文本决定业务分支，只依赖错误码、HTTP 状态和结构化字段。本期不实现国际化资源包。

### 3.3 API 兼容规则（必须）

1. 七天 MVP 统一使用 `/api/v1`，不预先建设空的 `/api/v2`。
2. 新增可选字段、可选查询参数或新端点属于向后兼容变更，可继续留在 v1；新增枚举值前必须同步 A、B、C 及所有实际调用方。
3. 删除字段、字段改名、改变类型/必填性、改变既有状态或错误码语义属于破坏性变更。原则上本期禁止；确需变更时必须经受影响负责人确认，并升 API 版本或保留旧契约至少一个联调周期。
4. 每个 API 版本导出独立 OpenAPI 文档；实现、Mock、调用方 DTO 和契约测试必须指向同一版本，不允许仅修改服务端路径。

### 3.4 OpenAPI 契约（必须）

1. 使用 SpringDoc OpenAPI 3 生成接口文档。开发和演示环境开放 `/v3/api-docs` 与 Swagger UI；生产环境默认关闭 Swagger UI，确需开启时仅允许内网或 `ADMIN` 访问。
2. Controller 使用 `@Tag` 和 `@Operation` 描述业务用途；请求/响应 DTO 使用 `@Schema` 声明含义、必填性、格式、枚举和示例。不得用注解重复解释显而易见的 Java 类型。
3. 全局 OpenAPI 配置声明 `Secure + HttpOnly Cookie` 认证、CSRF Header、`Idempotency-Key`、`Result<T>`、`PageResult<T>` 和通用错误响应；不得在文档中要求前端提交 Bearer Token。
4. 新增或修改接口时，同时更新实现、OpenAPI、调用方 DTO、Mock 和契约测试。提交联调前导出 `/v3/api-docs`，核对路径、方法、字段类型、必填项、枚举和错误码。
5. OpenAPI 是 REST 联调契约，不替代 Agent Tool JSON Schema、领域事件 Schema 或数据库迁移；四者分别维护，不允许由 Entity 自动推导并对外暴露。

### 3.5 写操作、幂等和响应丢失（必须）

1. 创建订单、支付、退款、取消、注册和验证码消费等可重试写操作必须使用稳定的 `clientRequestId` 或明确幂等键。
2. 同一用户、同一业务动作、同一幂等键的重复请求必须返回首次已确定结果，不能重复扣座、支付、退款或创建任务。
3. 写请求响应未知或丢失时，客户端/Agent 先查询权威状态；禁止无条件自动重放。
4. Agent 发起写工具时，除幂等键外必须校验确认凭证 `actionId`：未确认、过期、已消费或参数变化均拒绝执行。
5. 服务端生成金额、订单状态、票码和状态迁移；调用方只提交经校验的选择与确认。
6. 服务端为幂等请求保存“用户、动作、幂等键、参数摘要、业务结果”关系；同键同参数返回原结果，同键不同参数返回 409 和 `205005`，不得静默采用新参数。
7. 数据库最终约束至少覆盖：`userId + clientRequestId` 的建单唯一性、一个订单最多一条 Mock 支付记录、退款业务幂等键唯一性，以及 D 侧一个 `orderId` 最多一个提醒任务。Redis 防重不能替代这些约束。
8. `Idempotency-Key` 按动作隔离，创建订单、取消、支付和退款不得共用同一命名空间。幂等键不得包含密码、Token、邮箱等敏感数据，日志只记录摘要。

### 3.6 Agent 与 SSE 契约（必须）

1. Agent 只编排类型化工具；自然语言、模型输出或历史快照不得直接改变交易状态。
2. 工具调用固定为 `ToolContext + Command + ToolResult<T>`。`ToolContext` 字段为 `runId/nodeId/targetName/inputRefs/deadlineMs/traceId/clientRequestId/idempotencyKey/stateVersion`；写工具恢复时必须原样复用上下文，不生成新幂等键。
3. `Command` 只包含类型化领域参数；`userId`、角色、金额和状态不属于模型可提交参数。`createOrder`、`requestRefund` 的 `actionId` 属于 Command，且必须匹配确认记录的用户、动作、计划版本和 `parameter_hash`。
4. `ToolResult<T>` 公共字段严格对齐 B V1.8：`status,data,errorCode,retryable,replanSuggested,suggestedNextAction,degraded,fallbackType,stateVersion,dataAt,expiresAt`。不得另造 `recommendReplan`、`suggestedNextStep` 或 `dataTime` 等同义字段；不同工具的业务字段只放入类型化 `data`。
5. 内部只读工具超时为 3 秒，外部只读工具为 5 秒；只读工具最多重试一次且受 Agent 总时限约束。写工具禁止因超时、SSE 重连或重规划自动重试，只能用原上下文查询权威结果。
6. `ToolRouter` 只能调用注册表中的白名单工具。工具必须校验 Schema、资源归属、业务 ID、当前状态、金额和动态数据时效；动态结果缺少 `dataAt` 或 `expiresAt` 时不得用于后续写节点。
7. 前端仅根据结构化消息类型渲染 `TEXT`、`QUESTION`、`MOVIE_CARD`、`PLAN_CARD`、`ORDER_CONFIRM`、`REFUND_CONFIRM`、`PROGRESS`、`ERROR`；不得解析模型自然语言推断交易状态。
8. 支付不是 Agent 工具。Agent 只能返回独立支付页入口；SSE 只传输运行进度和卡片，不是交易提交、支付成功或提醒创建的事实来源。

## 4. 安全、认证与隐私

1. 所有受保护接口使用 Spring Security 鉴权；管理员接口额外要求 `ADMIN` 角色。前端隐藏菜单不等于后端授权。
2. JWT 仅放入 `Secure`、`HttpOnly`、`SameSite` Cookie；禁止写入 localStorage、sessionStorage、URL、日志和埋点。
3. 状态变更接口必须执行 CSRF 防护；CORS 仅允许明确白名单，不使用宽泛来源配合凭据。
4. 密码仅使用 BCrypt 等安全散列；验证码一次性消费并以条件更新保证并发下只能成功一次。注册唯一性由数据库唯一约束最终裁决。
5. 密钥仅来自环境变量或只读 Secret 文件；`.env`、私钥、Token 和生产配置不得提交版本库或写入镜像。
6. Redis 不可用时，不得绕过限流、会话失效或交易一致性校验；按模块定义失败关闭或降级策略并告警。
7. Mock 支付的六位模拟密码只在浏览器组件内做格式校验；后端请求 DTO、Controller、日志、Trace、数据库、Agent Tool、OpenAPI 和测试快照中均不得定义或接收 `paymentPassword`。
8. URL、重定向目标、动态排序、文件类型、工具名称和反序列化类型必须使用服务端白名单；不得将用户输入直接解释为类名、Bean 名、SQL 标识符或任意跳转地址。
9. 不记录或返回模型原始思维过程、系统提示词和完整 Agent 上下文；只保留为审计所需的结构化节点、工具名、脱敏输入摘要、结果状态与错误码。

## 5. 数据库、缓存与迁移

1. Schema 只通过版本化迁移变更；迁移只前进，不在应用启动代码中隐式改表。迁移文件一经进入共享环境不得修改历史内容；修复使用新版本迁移。破坏性删除不与依赖它的应用版本同批发布。
2. 表、列、索引和枚举变更必须同时提交：迁移脚本、回滚/兼容说明、Entity/Repository、接口影响和测试。
3. 交易表使用数据库约束守住唯一性和状态正确性；“先查询后插入”不能替代唯一索引或条件更新。
4. 读写缓存必须明确 key、TTL、失效策略与 Redis 故障行为；缓存不是订单、座位或支付的最终事实来源。
5. 固定 Mock 种子数据必须可重复运行、结果确定且不覆盖交易数据；种子脚本的幂等性纳入测试。
6. 所有查询按访问条件设计索引；提交新慢查询前用执行计划验证，不为每个查询盲目新增索引。
7. 不机械要求每个迁移提供反向 `rollback.sql`。发布前必须备份；应用失败时优先回滚应用版本，结构或数据问题通过新的前向迁移修复。不可逆操作必须在兼容说明中列出数据恢复来源和验证步骤。

### 5.1 MySQL 与 ORM 细则（必须）

1. 使用 InnoDB 与 `utf8mb4`。表名、字段名使用小写加下划线；表必须有主键、`create_time` 和 `update_time`。布尔字段数据库使用 `is_xxx`，Java 属性使用 `xxx` 并明确映射。
2. 业务唯一性必须通过唯一索引保证；索引命名使用 `uk_`、`idx_` 前缀。联合索引按等值查询、区分度和最左匹配原则设计。
3. 禁止外键、级联更新和存储过程；关联完整性、状态迁移与删除策略由应用层和事务控制，但不能省略数据库索引与唯一约束。
4. 查询只列出所需字段，禁止 `SELECT *`。`COUNT(*)` 用于统计行数；聚合函数可能返回 `NULL` 时须在 SQL 或代码中明确兜底。
5. 所有 SQL 参数使用预编译绑定；MyBatis/JPA 等框架中禁止将用户输入通过 `${}` 或字符串拼接直接写入 SQL。动态排序字段使用白名单映射。
6. 更新/删除前先确认影响范围；生产和演示修数必须先执行等价 `SELECT`。禁止无条件大范围 `UPDATE`、`DELETE` 和 `TRUNCATE`。
7. 更新语句应只更新本次业务所需字段；禁止“传入整个对象即全字段更新”的通用接口，防止覆盖并发修改和产生无效 binlog。
8. ORM 查询结果使用明确 Entity/DTO 映射，禁止使用 `HashMap`/`Hashtable` 承接业务查询结果；持久化实体不得穿透到 API 和 Agent Tool。
9. 主键和标识规则：
   - 内部业务表主键使用 `BIGINT` 雪花 ID；Java 实体使用 `@TableId(type = IdType.ASSIGN_ID)`。
   - 数据库主键不得配置 `AUTO_INCREMENT`，唯一例外是 `agent_event.event_id` SSE 游标。
   - `sys_user.id`由 C 生成，其他模块的 `user_id/currentUserId/recipientUserId`只复用该值。
   - UUID 业务标识和第三方原始 ID 使用字符串；REST/SSE/卡片中的 ID 输出十进制字符串。
   - 金额使用 `DECIMAL(10,2)` 和 `BigDecimal`；时间使用 `DATETIME(3)` 与 `java.time`。
   - 禁止使用 `double`、秒级时间戳或无时区字符串表示金额和时间。
10. 订单、支付、电子票、退款和审计记录不得物理删除。确需逻辑删除的非交易表要统一字段语义，并确保唯一索引、查询和恢复规则不与逻辑删除冲突。
11. 乐观锁字段统一使用 `version`；状态更新 SQL 必须同时检查允许的前置状态，必要时检查版本。影响行数不符合预期即视为并发冲突，不允许继续执行后续状态写入。

### 5.2 Redis 细则（必须）

1. Key 采用 `cinewise:{module}:{purpose}:{businessKey}`，模块、用途和业务键不可含敏感原文；每类 Key 在配置或设计中登记值结构、TTL、最大数量和失效策略。
2. Redis 只用于短期防重、限流、缓存和运行态辅助，不是座位、订单、支付、电子票、退款或确认消费的最终依据。Redis 命中与否不能覆盖 MySQL 权威状态。
3. 缓存更新采用“数据库提交后删除/失效”或明确的一致性方案；事务回滚时不得提前发布成功缓存。缓存穿透、击穿和大 Key 风险要按访问规模评估。
4. 若使用 Redis 锁，释放时必须原子比较持有令牌，锁要有有限 TTL；但交易正确性仍由数据库条件更新、唯一约束和事务保证。

## 6. 交易一致性红线

1. 原子建单必须在同一本地事务完成：幂等查询、场次/金额校验、全部座位条件锁定、订单和明细写入。任一座位失败，整体回滚。
2. 取消或超时只释放“属于该订单且仍为 LOCKED”的座位；重复执行返回当前结果，绝不释放其他订单座位。
3. 模拟支付要保证支付记录唯一、订单状态、座位 SOLD、电子票有效状态的一致迁移；HTTP/SSE 响应成功不等于交易成功，按订单查询为准。
4. 退票必须在确认和幂等校验后完成退款记录、订单 REFUNDED、电子票失效和座位释放；重复请求返回同一退款结果。
5. 支付成功后的提醒任务不放入支付事务；D 以 `orderId` 为业务幂等键创建唯一 `travel_task`，以 `eventId` 识别重复投递。失败由对账任务补建，不回滚支付。
6. 订单、支付、退款和座位状态只能经状态机允许的迁移改变；禁止 Controller/Mapper 直接更新状态字符串。

### 6.1 冻结状态迁移（必须）

| 聚合 | 允许迁移 | 禁止示例 |
| --- | --- | --- |
| 座位 | `AVAILABLE → LOCKED → SOLD`；取消/过期时 `LOCKED → AVAILABLE`；退票时 `SOLD → AVAILABLE` | 跳过锁座直接售出；释放不属于当前订单的座位 |
| 订单 | `PENDING_PAYMENT → PAYING → PAID → REFUNDING → REFUNDED`；`PENDING_PAYMENT → CANCELLED/EXPIRED` | `PAID → CANCELLED`；`EXPIRED → PAYING` |
| 支付 | `INITIALIZED → PROCESSING → SUCCESS` | 结果未知直接写失败；同一订单创建第二条 Mock 支付 |
| 电子票 | `VALID → REFUNDED/INVALIDATED` | 退款后恢复 `VALID` |
| 退款 | `REQUESTED → PROCESSING → SUCCESS` | 跳过请求记录直接释放已售座位 |

1. 状态枚举、数据库值、REST DTO、Agent Tool DTO 和前端展示值必须同名；展示文案另行映射，不修改状态值。
2. 每次迁移封装为有业务名称的应用服务方法或领域方法，同时校验当前状态、资源归属、过期时间和版本；禁止提供 `updateStatus(id, status)` 通用入口。
3. 响应超时只表示结果未知。客户端和 Agent 必须通过 `orderNo`、`clientRequestId` 或原幂等键查询；服务端不得把未知结果映射成支付失败或重新执行写操作。

### 6.2 原子建单编码顺序（必须）

1. 从认证上下文取得当前用户，并按 `userId + clientRequestId` 查询既有结果；同键参数摘要不一致返回 `205005`。
2. 在事务内重新读取场次、座位和服务端价格，校验场次可售、未开场、座位数量和版本；禁止使用前端或 Agent 提交的金额。
3. 对全部座位执行带 `show_id/status/version` 条件的更新，并绑定当前 `orderNo` 与过期时间；影响行数少于请求数量则抛出座位冲突，使整个事务回滚。
4. 写入订单和订单座位明细；唯一约束冲突时查询并返回原业务结果。事务提交后才允许刷新缓存或返回成功。

## 7. 事务、事件、外部调用与任务

### 7.1 事务边界（必须）

1. `@Transactional` 放在 Application Service 的公开用例入口；同类内部调用不会经过 Spring 代理，不得依赖自调用开启事务。
2. 事务方法默认遇到运行时异常回滚；受检异常是否回滚必须显式声明并测试。禁止捕获事务异常后返回成功，或在事务已标记回滚后继续写入。
3. 事务应短小，不包裹模型、天气、地图、邮件、对象存储或其他 HTTP 调用；跨模块同进程调用也必须遵守所属 Application API，不直接操作对方 Repository。
4. 多资源更新采用固定顺序；批量锁座必须先按 `seat_id` 升序排列，再以同一顺序执行条件更新，降低死锁风险。发生数据库死锁时仅在用例整体幂等且重试次数有界的前提下重试。
5. `@Async`、事件监听器和定时任务不会自动继承 HTTP 线程的认证与 MDC；必须显式传递最小业务上下文和 `traceId`，并在任务结束时清理 ThreadLocal/MDC。

### 7.2 支付成功事件（必须）

Mock 支付事务提交成功后，A 发布进程内 `PaymentSucceededEvent`；B 不监听，D 使用 `@TransactionalEventListener(phase = AFTER_COMMIT)` 消费。MVP 不为此引入消息队列，监听失败不能回滚已支付订单。

```java
public record PaymentSucceededEvent(
    String eventId,
    String orderId,
    String showId,
    String userId,
    String cinemaArea,
    OffsetDateTime startAt,
    long orderVersion,
    OffsetDateTime occurredAt
) {}
```

1. 字段名和语义必须与总体设计、A V1.2、B V1.8 一致；不得加入邮箱、邀请码、模拟密码、完整订单明细、二维码或模型上下文。
2. `eventId` 用于重复投递识别，D 以 `orderId` 为业务幂等键创建 `travel_task`，并用 `orderVersion` 丢弃旧事件；`travel_task` 的 Entity、Repository、DDL 和状态由 D 唯一拥有，A 不跨模块读写。
3. 事件类属于稳定跨模块契约，变更字段必须同步 A、D、总体设计和集成测试。消费者必须在独立事务中执行，唯一约束冲突返回原任务，不重复创建提醒。
4. A/D 每 5 分钟对最近 24 小时 `PAID` 订单做补偿对账，每批最多 100 条；缺少任务时从权威订单、场次、影院数据重建同结构事件。每轮记录扫描、补建、冲突、失败数量和耗时。
5. 支付作废或退票需要取消提醒时使用冻结的 `OrderInvalidated` 契约，复用上述字段并增加 `invalidReason`；不得通过删除支付成功历史掩盖状态变化。

### 7.3 定时任务（必须）

1. MVP 使用 Spring `@EnableScheduling` 与独立 `ThreadPoolTaskScheduler`，不引入 Quartz。默认池大小 4、线程名前缀 `cinewise-job-`、优雅停机等待当前任务，并配置统一 `ErrorHandler`，避免单次异常终止后续调度。
2. `ExpiredOrderReleaseJob` 每 30 秒扫描一次、每批最多 100 条：只处理 `status=PENDING_PAYMENT AND expire_time<=now` 的订单；逐单新事务条件更新为 `EXPIRED` 后，只释放 `lock_order_no=当前订单号 AND status=LOCKED` 的座位。
3. `TravelTaskDueJob` 由 D 实现，每 60 秒扫描、每批最多 100 条，复用 A 提供的调度配置；D 在自身 Repository 中按状态和触发时间条件抢占，A 不读取 `travel_task`。
4. 可选的 Mock 场次滚动任务每日 `00:10` 补齐未来第 7 天数据，以固定随机种子和自然业务唯一键 upsert，不覆盖已有交易数据。
5. 所有业务时间计算使用 `Asia/Shanghai`，持久化到毫秒；边界条件统一使用 `<= now`。测试必须注入 `Clock`，禁止在领域代码散落 `LocalDateTime.now()` 导致不可重复测试。
6. Job 只负责扫描和调用 Application Service，不直接写 Mapper。任务必须可重复执行、单条失败不回滚整批、失败项保持可再次扫描；服务重启后从数据库补扫，不依赖内存游标。
7. 单机 Compose 不依赖 Redis 分布式锁。未来多实例仍以数据库条件抢占和唯一约束作为最终保障；进程锁或 Redis 锁只能减少竞争，不能决定任务是否已执行。

### 7.4 外部调用与降级（必须）

1. 外部调用必须设置连接超时、读取超时、总预算、有限重试、错误映射和 Mock/降级；非幂等写调用不得自动重试。
2. 外部 DTO 在 Adapter 边界转换为内部类型，必须标注 `dataSource/dataAt/expiresAt/degraded/fallbackType` 等适用字段；过期或降级数据不能伪装成实时成功结果。
3. MinIO 在 MVP 中是可选的云端对象存储，只用于演示静态资源；电子票码由业务数据生成，不以 MinIO 可用作为支付、出票或验票成功条件。
4. 事件、任务和外部 Adapter 日志均携带 `traceId` 与业务关联 ID，不记录敏感原文。

## 8. 日志、异常与可观测性

1. 每个 HTTP 请求、Agent 运行、工具调用和异步任务传播 `traceId`；错误响应回传同一 traceId。
2. 业务可预期异常映射为稳定错误码和适当 HTTP 状态；未知异常统一返回通用错误，详细堆栈只在服务端日志中保留。
3. 关键交易日志记录：订单 ID、当前/目标状态、幂等键摘要、座位数、结果与耗时；不得记录完整用户输入或支付秘密。
4. 最低监控项：HTTP 延迟/5xx、锁座冲突、重复写拦截、订单状态异常、Redis/外部服务故障、Agent 工具失败和补偿任务失败。

## 9. 测试与变更关闭门槛

### 9.1 测试要求（必须）

- 新增或修改业务规则必须有单元测试；跨层、数据库、权限、事务或并发行为必须有集成测试。
- 修改接口必须更新契约/OpenAPI，并覆盖成功、参数错误、未认证、越权和关键业务失败场景。
- 修改 Agent 工具必须覆盖 Schema 校验、确认凭证、可重试语义和重复执行。
- 修改迁移或种子必须在空库和重复执行场景验证。
- 修改定时任务或事件必须覆盖重复触发、并发消费、单条失败、服务重启补扫和补偿对账。
- 测试名称表达“给定条件—执行动作—期望结果”；测试数据使用 Builder/Fixture，时间相关测试注入固定 `Clock`，不得依赖执行当天或测试顺序。

### 9.2 必须回归的高风险场景（必须）

1. 20 个并发在线用户、5 个并行 Agent 任务共同执行查询与交易时，不得超卖、重复建单或重复退票；另以 20 个请求竞争同一座位验证最多一个建单成功。
2. 同一 `userId + clientRequestId` 重复建单，返回同一订单；服务端成功但响应丢失后可恢复查询。
3. 重复取消、重复支付、重复退票均不重复改变状态或释放座位。
4. 用户 A 访问用户 B 的订单/票返回 404；普通用户访问管理接口返回 403。
5. Agent 缺失、过期、已使用或参数不一致的 `actionId` 不得改变交易数据。
6. SSE 重连、Agent 重规划和支付事件重复投递不产生重复写入或重复提醒。
7. Redis 或外部服务不可用时，按既定降级策略运行，不绕过安全与一致性规则。
8. 支付成功事件重复投递只产生一个 `travel_task`；消费者首次失败后可由下一轮重试或 5 分钟对账补建，且不改变订单 `PAID` 状态。
9. 过期释放任务在到期边界、重复执行和并发执行下只释放当前订单仍为 `LOCKED` 的座位；支付已开始或已成功的订单不得被释放。
10. 普通查询 P95 不超过 1.5 秒；锁座、建单、支付和退票 P95 不超过 2 秒，无法在预算内完成时返回可查询的处理中/结果未知状态，不伪造失败。
11. 自动化扫描确认六位模拟密码未出现在后端请求、OpenAPI、日志、埋点、URL、存储和 Agent 契约中。
